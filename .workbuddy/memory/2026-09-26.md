## 修复：父段 loading.tsx 遮蔽子段骨架（详情页先闪首页骨架）

**症状（用户报告）**：点进文章详情页，先出现一个 "loading"，再出现详情的骨架屏，像加载了两遍；先出现的那个根本不是详情骨架。

**根因（实测确证）**：`frontend/src/app/[locale]/loading.tsx` 渲染的是**首页骨架** `HomeSkeleton`，它是整个 `[locale]` 段的 Suspense fallback。Next.js 16.3 App Router 下父段 loading 会**抢在**子段 loading 之前渲染：

- 详情页 HTML 里 `<template id="B:1">` 后跟 HomeSkeleton（`hero-section` × 2）、`<template id="B:2">` 后跟 PostDetailSkeleton —— 两份 fallback 同时存在，外层先落地。
- 结果：`posts/[id]/loading.tsx`(PostDetailSkeleton)、`posts/(list)/loading.tsx`(PostsListSkeleton)、`(auth)/register/loading.tsx`(RegisterSkeleton) **三个骨架全是死代码**，从未被渲染。

**修复**：把首页连同它的 loading 收进路由组（零代码改动，URL 不变）：

- `app/[locale]/page.tsx`    → `app/[locale]/(home)/page.tsx`
- `app/[locale]/loading.tsx` → `app/[locale]/(home)/loading.tsx`

这样 `(home)/loading.tsx` 只包裹 `(home)/page.tsx`，不再污染 `posts/`、`(auth)/`、`(dashboard)/`。

**验证**（`curl -s <url> | grep -c hero-section`）：

| 路由 | 修复前 | 修复后 |
|---|---|---|
| `/zh` 首页 | 2（正确） | 4（正确，hero 骨架保留） |
| `/zh/posts/[id]` 详情 | 2（错） | **0** |
| `/zh/posts` 列表 | 2（错） | **0** |
| `/zh/register` 注册 | 2（错） | **0** |
| `/zh/xxx` 404 | 2（错） | 0 |

rAF 采样确认详情页 fallback 从「首页骨架 54 条」变为「详情骨架 49 条」，随后才切真实内容。
`pnpm typecheck` 通过；`pnpm build` 通过，路由表 `/[locale]` 仍是 `● /zh`、`● /en`（SSG），`/[locale]/posts/[id]` 仍是 `●` SSG。

**⚠️ 遗留（同类问题，未修）**：`app/[locale]/(dashboard)/loading.tsx`(DashboardSkeleton) 与 `profile|settings|write/loading.tsx` 是同构的「父段遮蔽子段」结构，但首屏被三重短路：

1. `proxy.ts` 对 PROTECTED_ROUTES 无 `auth_token` cookie 直接 302 到 `/login`；
2. 服务端 `requireUserOrRedirect` 再判一次；
3. `AuthGate`（`(dashboard)/layout.tsx`）SSR 时 `loading` 初值为真、直接渲染 DashboardSkeleton，子页面根本不被渲染。

→ 只在**已登录用户的客户端软导航**时可见。若要一并修，删 `(dashboard)/loading.tsx` 即可（AuthGate 已提供等价兜底）。需登录后自查。

## 排查手法（可复用）

- **Playwright 可用**：`~/.workbuddy/binaries/node/workspace/node_modules`（playwright 1.62.1），浏览器在 `~/AppData/Local/ms-playwright/chromium-1243`。
  跑法：`NODE_PATH=<workspace>/node_modules <managed node> script.cjs`，launch 参数带 `--no-proxy-server`，并 `unset HTTP_PROXY HTTPS_PROXY`。
- ⚠️ **本项目在无头浏览器里不会 hydrate**（`__reactFiber$` 检测为 false），`el.click()` 一律退化成整页重载，拿不到真正的软导航。
  → 改用 **SSR HTML 比对**更硬：`curl -s <url> | grep -o -E '<template id="B:[0-9]+"></template>.{0,160}'`，直接看每个 Suspense boundary 的 fallback 是哪个骨架。
- 骨架识别靠特征 class：`hero-section`(首页) / `page-header`(列表、设置、写) / `auth-card`(登录、注册) / `profile-cover-band`(个人主页) / `.bg-skeleton` 计数。
- `pnpm dev` 缓存在 `.next/dev`，`next build` 产物在 `.next`；**先 kill 端口 3000 再 build**（dev.mjs 只清 `.next/dev`，不碰生产产物）。
- 移过文件后若 `pnpm typecheck` 报 `.next/types/validator.ts` 找不到旧路径，属陈旧生成产物 —— 跑一次 `build` 后再 typecheck 即消失。

## 追加：同类的组级遮蔽已确证并修掉（dashboard）

**探针实验（新手法，比删文件做对照更快更安全）**：临时写 `(auth)/loading.tsx`，内容只有
`<div data-probe-loading="auth-group">PROBE_AUTH_GROUP_LOADING</div>`，然后 curl 组内子路由数命中：

| 路由 | 探针命中 | 说明 |
|---|---|---|
| `/zh/login` | 1 | 组级 fallback 生效 |
| `/zh/register` | 1 | 同上 |
| `/zh/posts/[id]`（组外对照） | 0 | 证明不是全局噪音 |

探针出现在 children 槽的 fallback 位置、先于 `auth-main` 正式内容流出。**结论：路由组即使自身没有
`page.tsx`，它的 `loading.tsx` 照样会被组内子路由渲染并遮蔽子骨架**（此前以为「无 page 的组级 loading 是死代码」，证伪）。探针测完已删除。

**修复**：删除 `app/[locale]/(dashboard)/loading.tsx`（DashboardSkeleton 通用版，遮蔽了 profile/settings/write 三个精确骨架）。
删前已确认三个子页各自都有 `loading.tsx`，不存在失去兜底的页面。`pnpm typecheck` + `pnpm build` 均通过，
路由表 `/[locale]/profile|settings|write` 仍为 `ƒ Dynamic`，未退化。

**⚠️ 仍留第二层（未改，需登录实测）**：`(dashboard)/layout.tsx` 只有 `AuthGate`，其 `loading` 分支渲染
`DashboardSkeleton`（通用「页头 + 三根横杠」）。SSR 时 `loading` 初值为真 → 子页面在服务端根本不渲染
（`children` 只作为 RSC payload 下发）。所以 dashboard 页的骨架顺序是
`AuthGate 通用骨架 → 子页精确骨架 → 内容`，删组级 loading 只消掉其中一层。
该层三种改法（占位改 `null` / 服务端读 cookie 作初值 / 让守卫接受页面专属骨架）都有取舍，**未擅自改**。
