## 部署平台调研：Netlify 超限后的替代方案

**背景**：Netlify 免费层已无法继续部署，需要换平台。项目形态 = Next.js 16.3.5（App Router）+ Prisma 6.19 + `@prisma/adapter-neon` + `@neondatabase/serverless`（边缘友好驱动）+ pnpm monorepo（`frontend/` + `shared/`）+ next-intl 国际化 + JWT/bcryptjs 鉴权。当前 `netlify.toml` 用 `@netlify/plugin-nextjs` 跑 SSR。

**为什么被卡（关键）**：Netlify 于 2025-09-04 改计费模型 —— 不再是「100GB 带宽 + 300 构建分钟」，而是**单一 300 credits/月的信用池**（生产部署 15 credits/次、带宽 20 credits/GB、web 请求 2 credits/1 万、compute 10 credits/GB-hr）。折算上限：纯流量 ≈15GB，或纯部署 ≈20 次。超限会**暂停账号下所有项目**（不只是超支的那个）。2025-09-04 前注册的老账号可能仍在旧模型。

**调研结论（2026-09-24 核实）**：

| 平台 | 免费额度 | Next.js 服务端 | 国内访问 | 判断 |
|---|---|---|---|---|
| **EdgeOne Makers（腾讯云）** | 500 构建/月、流量与请求不限量、300 万边缘函数 + 100 万云函数请求/月、KV/Blob 各 1GB（数字源自社区文章，需控制台复核） | 支持 SSR/ISR/SSG/RSC/Streaming/Middleware/Route Handlers，输出 `.next` | 备案域名 50–90ms（最优）；未备案 670–1400ms | **首推** |
| Cloudflare Workers | 带宽不计量、10 万请求/天、允许商用 | 需 `@opennextjs/cloudflare` 改造；10ms CPU 硬限 | 联通晚高峰 800ms+ | 备选 |
| Vercel Hobby | 100GB + 100 万调用/月 | 零配置原生 | **国内打不开** | 排除（且禁商用） |
| Render | 750 实例小时/月、5GB 带宽 | 支持（next start） | 一般；闲置 15 分钟休眠、冷启动约 1 分钟 | 不推荐给博客 |

## 【第四轮】Cloudflare 路线排除 + 浏览器 MCP 连接方式（提交 `e637a57`）

**用户动作**：在 Cloudflare 注册了账号并建了一个名为 `my-app` 的 Worker（面板截图），要求我「直接访问浏览器」帮忙看哪里没配置好。

### ⚠️ 浏览器 MCP 的关键机制（以后会反复用到，别忘）

- `chrome-devtools` MCP 的**默认行为是自建一个独立 Chrome**，用专用 profile：Windows 下 `%USERPROFILE%\.cache\chrome-devtools-mcp\chrome-profile`（**不随运行清空，跨会话保留登录**）。**它不会自动挂到用户正在用的 Chrome 窗口** —— 所以 `list_pages` 只看到 `about:blank`，用户体感是「你怎么新开了个浏览器」。
- 挂到**用户现有 Chrome** 的两条官方路径（`chrome-devtools-mcp` 仓库 `docs/advanced-usage.md`）：
  1. **`--autoConnect`（推荐，要求 Chrome ≥ M144）**：用户在 Chrome 里打开 `chrome://inspect/#remote-debugging` 启用远程调试并允许连接；MCP args 里加 `--autoConnect`。连的是**默认 profile，含全部标签与登录态**。本机 Chrome = **153.0.8010.53**，满足要求。
  2. `--browser-url=http://127.0.0.1:9222` + 以 `--remote-debugging-port=9222 --user-data-dir=<非默认目录>` 启动 Chrome。⚠️ **Chrome 安全策略要求必须用非默认 user-data-dir** → 因此**拿不到用户的登录态**，只适合沙箱穿透场景。
- 已把 `~/.workbuddy/mcp.json` 的 chrome-devtools args 改为追加 `--autoConnect`。**需用户重启 WorkBuddy 生效，且必须先在 Chrome 里打开那个开关**；开关没开时浏览器工具会连不上。回滚：删掉该 arg 即恢复自建浏览器。
- 该 MCP 浏览器实例访问 `dash.cloudflare.com` 会卡在加载页（SPA + 无登录态），不要用它去读需要登录的后台。

### Cloudflare 判定：此路不通（两条相互独立的硬障碍）

- **`*.workers.dev` 实测不通**：根域超时 8s；`example.workers.dev` / `abcxyz123.workers.dev` 均 **10.0s 超时**；对照组 `pages.dev` 0.91s 正常（同属 Cloudflare，解析 `104.18.20.135`）→ 被阻断的是**通配域本身**，不是测试方法问题。（v3 只测了根域，有假阴性风险，本轮已补正。）
- **官方 Limits：Free 档 CPU 10ms 硬上限且不可调**（仅 Paid 可改 `limits.cpu_ms`）；官方原文自述 *"workloads that handle authentication, server-side rendering … typically use 10-20 ms"*。本项目 `bcryptjs` 单次 80–100ms → 必然 `Error 1102`。
- 要用 Cloudflare 须同时满足「Workers 付费 $5/月 + 自有域名」，**两项都不是 ¥0**。
- 仓库内**零** Cloudflare 配置（无 `wrangler.jsonc`、`package.json` 无 `@opennextjs/cloudflare` 依赖）→ Git 仓库直接导入跑不起来（`.next` 产物 Workers 吃不下）；控制台那个 `my-app` Worker 与本项目无关。
- 另：OpenNext 的 Cloudflare 适配器把 Next.js 部署到 **Workers**，不是 Pages —— 所以 `pages.dev` 可达并不构成可用路线。

**仍缺的信息**：用户线上博客的**实际地址**（仓库里没有任何记录，`grep netlify.app|workers.dev|edgeone.app|vercel.app` 为空）。诊断登录态问题或核对 `NEXT_PUBLIC_BASE_URL` 时需要它。

**提交**：`e637a57`（`DEPLOYMENT.md` §7.3 补实两条障碍的实证与官方原文），已推送。

## 【第五轮】Cloudflare 二次复核 + 浏览器连接可行性

**用户诉求**：要求「直接操作我正在用的浏览器」，不接受我另开实例。

**浏览器连不上的根因（硬事实，有证据）**：
- 本机 `netstat` 扫描 9220–9230 及全部 127.0.0.1 监听端口 → **Chrome 一个调试端口都没开**。Chrome 从设计上禁止外部程序静默连接正在运行的实例，这是安全边界，不是工具配置问题。
- 追加 `--autoConnect` 后的 `chrome-devtools` MCP 工具从索引中消失（ToolSearch 找不到）→ 推测 `--autoConnect` 模式下无可连目标时 MCP 进程起不来。**结论：必须用户先开 `chrome://inspect/#remote-debugging` 开关，再重启 WorkBuddy，工具才会回来。**
- ⚠️ 实测偏差：`--browser-url` 路径要求非默认 `--user-data-dir`，**拿不到用户登录态** → 对「读需要登录的 Cloudflare 后台」这个目标是无效的。所以带登录态的自动化只有 `--autoConnect` 一条路。
- **更好的替代方案（本轮结论）**：让用户给一个 **Cloudflare API Token**（My Profile → API Tokens → "Edit Cloudflare Workers" 模板），我直接用 API 读/改/部署 Worker，完全绕开浏览器。这比 Chrome 授权更可靠、且不需要重启。

**Cloudflare 二次核实（2026-09-24，官方文档）**：
- **10ms CPU 限制未变** —— 官方《Limits》页当前仍写 Free 档 `CPU time per HTTP request = 10 ms`（Paid 默认 30s 可调至 5min）。`bcryptjs` 80–100ms 的结论依然成立。
- **官方 Next.js 部署路径已换代**：从 `@opennextjs/cloudflare` 改为推荐 **`vinext`**（Vite 插件重实现 Next.js API 面，**beta**），带 `npx vinext check` 兼容自检，官方还配了 agent skill（`npx skills add cloudflare/vinext` + prompt "migrate this project to vinext"）。**但换代不解决 CPU 与域名两堵墙。**
- **Cloudflare Pages 免费档**：500 builds/月、1 并发、静态带宽不限量、允许商用、无站点数上限 → `pages.dev` 可达（0.91s）。**这是 Cloudflare 上唯一 ¥0 可行的形态，但需静态导出、会砍掉登录/评论/后台。**
- **Workers Builds 对 monorepo 支持有限**（官方《Deploy an existing project》原文：*"does not detect dependencies installed at the workspace root"*）→ 本项目 `frontend` 依赖 workspace 根装的 `shared`，Git 导入时框架探测可能直接失败。这是本项目特有的第三个坑。
